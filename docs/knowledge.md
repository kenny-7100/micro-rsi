# 经验沉淀方法

## 什么时候记录

在完成任务过程中，判断新发现是否有助于未来复用、避免重复踩坑或理解重要决策。有价值时直接更新文档，并在交付中简要说明。以下情况通常值得记录：

- 实际发生的问题，以及经验证有效的原因分析、解决方法和验证方式。
- 可重复使用的操作流程、调试手段或实验方法。
- 会影响后续工作的设计决策、适用条件和取舍。
- 训练或评估发现的规律，但应附实验条件与证据，避免把单次结果泛化。

一次性输出、普通命令成功记录和完整对话流水通常不收录。没有新经验时不必为了留痕新增文档。

## 放在哪里

| 内容 | 位置 |
| --- | --- |
| 稳定、普遍适用的协作规则 | 根目录 `AGENTS.md`，保持简短 |
| 工程、数据、验证的具体要求 | `docs/engineering.md` |
| 阶段目标与验收变化 | `docs/roadmap.md` |
| 环境问题、可复用操作方法 | 对应主题文档，例如 `docs/local-environment.md` |
| 新的独立主题 | 新建语义清楚的文档，并更新 `docs/README.md` |
| 原始实验日志、权重、生成样本等产物 | `runs/` 或 `artifacts/`；文档只保留必要摘要与定位方式 |

同一结论只维护一份正文，其余位置通过链接引用。技术细则增长时优先整理 `docs/`，不要持续扩充 `AGENTS.md`。

## 怎样写才有用

自行编写或维护的沉淀文档优先使用中文，便于中文母语者理解和学习；第三方下载或引入的文档可以保留原文，无需强制翻译。技术专有名称、命令、路径和 API 名称保留原文，必要时配中文解释。

按需写清以下内容，不要求每条记录都套用完整模板：

1. 场景与条件：设备、版本、任务或触发操作。
2. 问题或决策：观察到的现象，或需要解决的选择。
3. 方法与原因：有效步骤、关键命令及选择依据。
4. 验证与限制：实际验证了什么，哪些仍是推测，何时需要重测。

区分已验证事实、推测和计划。涉及版本或性能时记录日期与实验条件；不保存凭据、隐私信息或冗长终端输出。

## 怎样维护

先查找已有主题并就地更新，必要时合并重复内容。新证据推翻旧结论时修正文档，并解释影响；有历史价值才保留旧方案及其失效条件。代码、命令或项目状态改变时同步更新相关说明和导航。
